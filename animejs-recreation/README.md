# BRIDGE Twin — scroll-driven 3D product page

A product page for **BRIDGE Twin**, a real-time digital twin of a large
commercial turbofan. One persistent WebGL canvas carries a procedurally-modelled
engine through a scroll-driven sequence of assembled, exploded and
technical-drawing states, with nine live instrumentation demos rendered inside
its circular front display.

The page's *layout and motion design* are a clean-room recreation of the
Anime.js landing page (see `REFERENCE_NOTES.md` for the measurement work);
the *content and identity* are BRIDGE's own.

Nothing is copied from the reference site: the 3D model is generated by a
Blender Python script in this repo, and all markup, CSS and TypeScript are
original.

## Regenerating the 3D model

The model is authored entirely in Python — there is no manual modelling step.

With Blender running and the MCP add-on enabled, run:

```python
exec(open(r"blender/build_model.py").read())     # build 55 named parts
exec(open(r"blender/preview_render.py").read())  # optional reference renders
exec(open(r"blender/export_glb.py").read())      # save .blend + export .glb
```

Or headless:

```bash
blender --background --python blender/build_model.py --python blender/export_glb.py
```

Outputs:

- `blender/anime_engine.blend`
- `public/models/anime-engine.glb`

Each part carries custom properties (`explode`, `grp`, `order`) that survive
into the glTF via `export_extras`, so the web scene reads every part's exploded
direction straight off the node instead of duplicating the table in TypeScript.

## Architecture

```
blender/
  build_model.py      procedural hard-surface model, 55 named parts
  preview_render.py   model-relative camera rig for reference renders
  export_glb.py       .blend save + glTF export
public/
  models/anime-engine.glb
  bridge-logo.svg
src/
  main.ts             orchestrator + render loop
  content.ts          every string, colour, section and route
  styles.css          all layout, measured from the reference
  scene/
    createScene.ts    renderer, camera rig, lighting
    loadModel.ts      glTF load, part registry, lens projection
    materials.ts      solid PBR mode + hidden-line technical mode
    sceneStates.ts    declarative keyframes + interpolation
    modelController.ts applies a resolved state to the model
    scrollController.ts scroll -> progress, rAF loop, visibility gating
  demos/              the nine in-lens animations
  ui/
    sectionLayout.ts  builds the whole document from content.ts
    codeCards.ts      code cards + syntax highlighting
    progressIndicator.ts the timeline scrubber
    lensOverlay.ts    projects the DOM demos onto the glass
tests/visual.spec.ts
```

### The one idea worth knowing

**The entire page is a pure function of a single number** — progress through the
21-viewport sticky stage track. `resolveState(p)` interpolates between
declarative keyframes to produce the background, camera, per-part explode
offsets, material mode, LED colours and overlay opacities. Nothing is a one-shot
tween, which is why scrolling back up retraces exactly and the model never jumps
between sections.

### Lens overlay

The nine feature demos are DOM/SVG, not textures, because the reference shows
crisp vector shapes and a genuinely draggable element. To keep them welded to
the glass, `Front_Display` is projected to screen space every frame and the
overlay gets a single `translate + scale`. Each demo authors against a fixed
600 × 600 design box and never reads the viewport, so alignment survives any
camera move, viewport size or zoom level. The overlay dissolves as the lens
turns away from camera, since a flat DOM plane cannot foreshorten.

### Technical-drawing mode

The two light sections use real hidden-line rendering rather than a wireframe:
every mesh is swapped to an unlit material painted the *same colour as the
background* and pushed back with a polygon offset, while pre-built
`EdgesGeometry` feature edges (28° threshold) draw on top. Faces therefore
occlude the edges behind them, giving the clean CAD look instead of a mess of
internal triangulation. The edge geometry is built once, lazily, the first time
the page approaches a light section.

## Performance

- One `WebGLRenderer`, one canvas, for the whole page.
- Device pixel ratio capped at 1.75.
- The rAF loop stops entirely when the tab is hidden.
- Allocation-free hot path: scratch vectors/colours are module-level.
- `EdgesGeometry` built once and cached; never rebuilt per frame.
- Demos pause when their section leaves the viewport.
- Camera distance scales up on narrow viewports so the model still fits.
- The GLB is Draco-compressed: **3.79 MB → 515 KB**, decoded with a locally
  served decoder (no CDN dependency) that is disposed after the single load.
- `prefers-reduced-motion` pins the scene to a static representative state,
  disables the idle spin and the typewriter, and unpins the sticky stages so all
  content stays reachable.

## Known differences from the reference

Tracked in full in `REFERENCE_NOTES.md` §10. The short list:

1. **Typeface** — the reference uses a licensed variable DIN. This build
   substitutes **Archivo Variable** at `font-stretch: 112%`, bundled offline via
   `@fontsource-variable` so Playwright renders are deterministic.
2. **Model proportions** — the brief suggested a 5.5–6 BU length at radius 2.2
   (1.3 : 1). The supplied screenshots clearly show a ~2.5 : 1 barrel, and the
   screenshots outrank the brief's own numbers, so radius stayed at 2.2 and the
   length went to ~11 BU.
3. **Brand and content** — the identity is BRIDGE (supplied wordmark in the
   header and footer, auto-inverted on the light sections) and the copy is a
   digital-twin product narrative, not the reference's animation-library copy.
   The multi-hue per-section accent system is kept, because it is structural to
   the layout being recreated rather than brand colour.
4. **Sponsor section** — repurposed from the reference's sponsor wall into an
   integrations strip (STEP AP242, ARINC 429, OPC UA, MQTT Sparkplug, Parquet,
   S1000D). No third-party names from the reference are reproduced.
5. **Toolbox diagonal** — the reference's first technical beat sits at roughly
   40° across the frame; this build lands closer to 25°. The subsequent
   vertical and horizontal beats match.
